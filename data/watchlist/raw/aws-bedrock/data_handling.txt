•	Customer prompts/outputs: AWS states that Bedrock customer inputs and outputs are not used to train Amazon's or third-party providers' foundation models under the standard Bedrock data-handling model. (https://aws.amazon.com/bedrock/security-compliance/) AWS also states that model providers do not have access to Amazon Bedrock logs, customer prompts or completions in the standard deployment architecture. (https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)
	•	Retention: Bedrock now provides configurable data-retention modes, including zero-data-retention (ZDR) behavior. Customers can control whether prompts and outputs from inference requests are retained. (https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html)
	•	Critical exception: Some newer models can require provider data sharing/retention. AWS documentation states that if a model requires provider data sharing, customers must explicitly configure the appropriate retention mode before invoking that model. (https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html)
	•	Abuse detection: AWS may retain certain inputs/outputs for automated abuse detection for particular models/use cases. AWS's abuse-detection documentation states that Bedrock generally uses a zero-data-retention model but identifies exceptions where data may need to be retained. (https://docs.aws.amazon.com/bedrock/latest/userguide/abuse-detection.html)
	•	Logging: Model invocation logging is disabled by default, but customers can enable it and send full request/response data and metadata to their own S3 bucket or CloudWatch Logs. Once enabled, logs remain until the logging configuration is deleted. (https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)
	•	Encryption: AWS states that Bedrock data is encrypted in transit and at rest, and customers can manage encryption keys using AWS KMS. (https://aws.amazon.com/bedrock/security-compliance/)
	•	Network controls: Bedrock supports AWS PrivateLink/VPC connectivity, allowing customers to connect privately without exposing their VPC traffic to the public internet. (https://aws.amazon.com/bedrock/security-compliance/)
	•	Data residency: Bedrock can process inference within a selected geographic boundary using Geographic Cross-Region Inference, such as EU-only processing. However, inference data can move between AWS Regions within that geography. (https://docs.aws.amazon.com/bedrock/latest/userguide/geographic-cross-region-inference.html)
	•	Global inference: Global Cross-Region Inference can route requests to commercial AWS Regions worldwide. Organizations with strict residency requirements therefore need to explicitly prevent global inference where necessary. (https://docs.aws.amazon.com/bedrock/latest/userguide/global-cross-region-inference.html)
	•	Subprocessors / third parties: Bedrock provides models from third-party model providers including companies such as Anthropic, Cohere, Meta and others. AWS's standard architecture is designed so those model providers do not receive ordinary Bedrock customer prompts/completions; however, specific models can impose provider-data-sharing requirements, so model-by-model contractual/data-flow review is necessary. (https://aws.amazon.com/about-aws/whats-new/2023/09/amazon-bedrock-generally-available/) (https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html)
	•	Customer-controlled storage: When customers enable invocation logging, the destination can be an S3 bucket or CloudWatch Logs resource in the same AWS account and Region, giving the customer considerable control over stored inference data. (https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)
	•	Overall data-handling assessment: Strong but configuration-dependent. The biggest risk is not the standard Bedrock architecture; it is inadvertently enabling logging, selecting models with provider-retention requirements, or using global/cross-region inference without considering residency obligations.
