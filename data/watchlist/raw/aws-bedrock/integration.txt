**How they integrate**: Amazon Bedrock offers:- **APIs** (including the Converse API for chat-based interactions)- **SDKs** (including the open-source `bedrock-agentcore` Python SDK)- **No-code/low-code** options within the AWS console- Integration with AWS services (Knowledge Bases, Guardrails, Agents, Bedrock Data Automation)**Export and leaving**: - Bedrock does not store customer prompts or outputs by default, so there is minimal customer data to export.- However, if you build applications using Bedrock's higher-level services (Agents, Knowledge Bases, Guardrails), you may have configuration data, vector embeddings, and agent definitions stored in AWS.- For Bedrock Data Automation (BDA), there is "currently no documented method to export an optimized blueprint" to another account.- Switching away requires re-implementing your application's AI integration with another provider's API—a software engineering effort rather than a data portability issue.**Known integration failures**: - IAM permission complexity is a frequent pain point.- Quota denials can break production.- A recent policy change for certain Anthropic models requires opting into data sharing, which some see as breaking Bedrock's "neutrality" promise.**Dependencies**: Bedrock is a managed service running on AWS infrastructure. It relies on:- AWS IAM for authentication and authorization- AWS KMS for encryption- AWS CloudTrail for audit logging- Third-party model providers (Anthropic, Meta, etc.) for the actual model inference**Lock-in risk**: Moderate. The primary lock-in is not data (since Bedrock doesn't store it) but **workflow lock-in**—if you've built complex agents, guardrails, or knowledge bases using Bedrock's proprietary services, migrating those to another platform requires significant re-engineering. The service is designed to be model-agnostic, which reduces model-layer lock-in, but AWS-specific constructs create platform lock-in.
