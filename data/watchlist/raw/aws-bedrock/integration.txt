•	API: Bedrock provides a fully managed API, including Bedrock API endpoints and model-invocation APIs. (https://docs.aws.amazon.com/bedrock/latest/userguide/api-reference-overview.html)
	•	SDKs: AWS provides SDK support and API references for programmatic integration. Bedrock can also be accessed through AWS CLI and SDKs. (https://docs.aws.amazon.com/bedrock/latest/userguide/api-reference-overview.html)
	•	Console / visual tooling: Bedrock includes console-based capabilities and managed features for building generative-AI applications, including Agents, Knowledge Bases, Guardrails and other managed components. (https://docs.aws.amazon.com/bedrock/)
	•	No-code classification: It is not primarily a no-code platform. The console allows substantial configuration and experimentation, but production applications normally involve APIs, IAM, AWS infrastructure and application code. AWS describes Bedrock as a fully managed service rather than a standalone no-code application builder. (https://docs.aws.amazon.com/bedrock/)
	•	Integration with AWS: Bedrock integrates deeply with AWS services including IAM, CloudWatch, CloudTrail, S3, VPC/PrivateLink and other AWS infrastructure. (https://aws.amazon.com/bedrock/security-compliance/)
	•	Exportability: Customer-owned source data and logs can reside in customer-controlled AWS resources such as S3 and CloudWatch. This makes raw data export relatively straightforward. (https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)
	•	Application portability: The inference layer is less portable than raw data. Applications can become dependent on Bedrock-specific model IDs, Agents, Knowledge Bases, Guardrails, Prompt Management, Flows, IAM policies and AWS-specific APIs. Migrating those components to Azure AI Foundry, Google Vertex AI or direct Anthropic/OpenAI APIs can therefore require engineering work. AWS's own model lifecycle documentation explicitly requires customers to modify application code when models reach EOL. (https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)
	•	Model lock-in: Bedrock reduces some model lock-in because it provides access to multiple foundation-model providers through one managed service. However, individual model APIs and capabilities are not necessarily interchangeable, and model-specific functionality can create application dependencies. AWS explicitly documents different endpoints/API support and model-specific capabilities. (https://docs.aws.amazon.com/en_us/bedrock/latest/userguide/models.html)
	•	AWS ecosystem lock-in: Medium-to-high if the implementation uses many native AWS components around Bedrock. Community reviews specifically identify AWS ecosystem lock-in as a concern. (https://www.g2.com/products/aws-bedrock/reviews)
	•	Breaking-change/deprecation risk: AWS has a formal model-lifecycle process. Legacy models receive a transition period, but after EOL requests can fail and customers must migrate themselves. (https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)
	•	Known integration issues: Community reports cite SDK/documentation inconsistencies, model-access problems, quota limitations and difficult debugging. These are user reports rather than independently verified AWS defects. (https://www.reddit.com/r/aws/comments/1qt3gne/aws_bedrock_in_production_anyone_else_finding_it/) (https://www.reddit.com/r/aws/comments/1pe72an/does_aws_bedrock_suck_or_is_it_just_a_skill_issue/)
	•	Overall lock-in assessment: Medium. Raw data is comparatively portable, and the multi-model architecture reduces dependence on one foundation-model provider. The bigger lock-in risk comes from adopting Bedrock-specific orchestration and AWS-native infrastructure around the model layer.
	•	Overall vendor-risk assessment: LOW financial/vendor-survival risk, LOW-to-MEDIUM security risk, LOW-to-MEDIUM compliance risk, MEDIUM integration/lock-in risk, and MEDIUM model-lifecycle risk. The principal procurement concern is therefore not whether Amazon will disappear, but whether the specific Bedrock models, APIs, regions and managed AI components selected today will remain available and compatible with the application's architecture.
